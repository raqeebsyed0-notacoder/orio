## 2. Root causes

- F1: `LoadGate`'s `empty` branch replaced the ENTIRE view — including the
  search/segmented/rail controls that produced the empty result — while the
  copy told the user to "Clear the filters", a control that was not rendered.
  Rigs was session-sticky because the query persists in the `rigq` storage
  key, so remount could not recover (escape = devtools only).
- F2: the plugin calls `jsx()`/`jsxs()` directly (uncompiled ESM). React 19
  dev-build rules, read off the bundled `react/jsx-runtime` source:
  `jsx()` + `key` inside props = key-spread warning; `jsx()` + array
  children = unique-key warning (arrays are only auto-validated when passed
  through `jsxs()`); `jsxs()` + non-array children = static-children error.

## 3. Fix (smallest structural change, in-system design)

- New `FilterEmpty` component (`desktop/plugin.js`, next to `LoadGate`):
  EmptyState + explicit `Clear filters` button, rendered INSIDE the view's
  content slot only. Filter chrome (search, segmented groups, rails, result
  counts, summary panels) stays mounted unconditionally.
- Per-view `clearAll` wired to the button:
  - Today: priority + search. Rigs: search + stage + page + `storageSet('rigq', '')`
    (explicit wipe; the persisting effect covers it too — the sticky brick
    cannot recur). Market Intel: all nine filter states + page + drilldown,
    back to defaults (COUNTED, report-date basis). Exceptions: state rail.
    Actions: state rail (button hidden when the queue is genuinely clear,
    `onClear=null`, copy directs to the rail instead).
- Empty copy rewritten per view to name only controls on screen
  ("the search field or the stage rail", "the snapshot rail", "the filters above").
- `LoadGate` itself untouched; the five views (+Actions) simply stop passing
  `empty:` — loading/error behavior identical. No `empty:` prop remains in
  any view (grep-verified).
- Persisted-key enumeration: `rigq` is the ONLY persisted view-filter key
  (`view`/`day` are global nav state, intentionally not cleared).
- F2 in touched views (Today+SnapshotRail+Donut, Actions, Rigs, Exceptions,
  Market Intel, shared THead): every `key`-in-props moved to the `jsx()`/
  `jsxs()` third argument; every array-children call goes through `jsxs()`;
  every single-child call through `jsx()`. Zero behavior change (key never
  reaches components either way; `jsx`/`jsxs` are identical except dev
  validation).
- Two self-caught regressions during verification (both fixed, both covered
  by re-run): Exceptions rail aside converted to `jsxs` with a single child,
  and the MI summary-leader string branch through `jsxs`, each raised the
  static-children error — caught by the harness, fixed, re-verified green.
